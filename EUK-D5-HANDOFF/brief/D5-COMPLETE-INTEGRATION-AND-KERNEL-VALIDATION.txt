# 5. PHASE TWO — INTEGRATE ALL SEVEN MODULES

Integrate each existing D5 module into the canonical kernel.

## 5.1 preempt.rs — Preemptive scheduling

Preserve the existing D5 implementation.

Integrate it with:

- Existing scheduler.
- Existing thread structures.
- Existing runqueue.
- Timer infrastructure.
- IRQ handling.
- Trap and interrupt frames.
- Kernel stack management.

Requirements:

- Timer interrupts must be able to request scheduling.
- A thread that never voluntarily yields must not monopolize the CPU.
- Non-preemptible sections must be respected.
- Blocking operations must be rejected when blocking is unsafe.
- Interrupt state must be handled correctly.
- Context switches must preserve execution state.
- Nested interrupt and preemption conditions must be handled safely.

Verify that the timer interrupt actually reaches the scheduling decision and that the context switch is safe.

## 5.2 sync.rs — Kernel synchronization

Preserve existing D5 synchronization logic and tests.

Integrate:

- Mutexes.
- Semaphores.
- Wait queues.
- Condition variables.
- Lock-order enforcement.
- Deadlock prevention.
- Priority inheritance.

Requirements:

- Blocking locks must cooperate with the scheduler.
- Wakeups must safely move threads into runnable state.
- Interrupt-context restrictions must be enforced.
- Lock ownership must remain consistent through thread termination.
- Priority inheritance must propagate and be reversed correctly.
- Synchronization must remain safe under preemption.

Do not implement fake blocking using busy loops.

## 5.3 process.rs — Process lifecycle

Preserve the existing process model.

Integrate process ownership with:

- Kernel threads.
- Address spaces.
- ELF loading.
- Memory limits.
- Parent-child relationships.
- Exit status.
- Resource cleanup.

Requirements:

- Process creation must establish valid ownership.
- Threads must belong to the correct process.
- Process termination must handle active threads safely.
- No thread may continue accessing freed process resources.
- Child and parent lifecycle transitions must be correct.
- All resources must be reclaimed exactly once.
- Failed creation must roll back partially allocated resources.

## 5.4 address_space.rs — Virtual memory and isolation

Integrate with existing physical-frame allocation and page-table infrastructure.

Requirements:

- Correct x86-64 page-table management.
- Correct user/kernel permission separation.
- Read, write and execute permissions must be enforced.
- Address-space ownership must be explicit.
- Page-table memory must be reclaimed safely.
- Shared kernel mappings must remain correct.
- User mappings must not expose kernel memory.
- Mapping and unmapping failures must roll back correctly.

Implement and validate actual CR3 switching.

Do not claim address-space switching is operational merely because the page-table code compiles.

## 5.5 usermode.rs — Ring 3 and system calls

This is a high-risk component.

Preserve existing validation and fault-handling logic.

Integrate:

- GDT.
- IDT.
- TSS and privilege-transition stack configuration.
- Trap handling.
- Syscall entry and return.
- User-pointer validation.
- Process termination on fatal user faults.

Requirements:

- Correct privilege transition from Ring 0 to Ring 3.
- Correct stack configuration.
- Correct interrupt and syscall entry.
- Correct register preservation.
- Correct return to user mode.
- Safe system-call argument validation.
- Invalid user pointers must not permit kernel memory access.
- Fatal user faults must terminate the affected process safely.

## 5.6 elf.rs — Executable loading

Preserve existing ELF validation and malformed-input tests.

Integrate the loader with:

- Process creation.
- Address-space management.
- Physical-frame allocation.
- User stack creation.
- User entry-point setup.
- Process lifecycle and rollback.

Requirements:

- Validate ELF headers and program headers.
- Reject malformed and unsupported inputs.
- Enforce segment permissions.
- Initialize BSS correctly.
- Prevent invalid mappings.
- Prevent user/kernel mapping violations.
- Roll back all allocations when loading fails.
- Ensure the entry point and stack are valid before entering user mode.

## 5.7 tls.rs — Thread-local storage

Integrate existing TLS logic with:

- Thread creation.
- Thread destruction.
- Context switching.
- CPU initialization.
- FS/GS register management.
- Relevant model-specific registers.

Requirements:

- Each thread must receive the correct TLS context.
- Switching threads must switch TLS state correctly.
- FS/GS state must not leak between threads.
- Destruction must reclaim TLS resources.
- CPU-local and thread-local data must remain distinct.

## 6.1 FPU/SSE context preservation

FPU/SSE state is not currently preserved across preemption.

Implement correct floating-point and SIMD context management.

Investigate:

- CPU feature detection.
- CR0 and CR4 configuration.
- XSAVE/FXSAVE availability.
- Required alignment.
- Per-thread state allocation.
- Context save and restore.
- Lazy versus eager state switching.
- Interrupt and exception interactions.

Choose the safest implementation compatible with the kernel's CPU target.

Do not enable unsupported instructions.

Test that two independently scheduled threads cannot corrupt one another's floating-point or SIMD state.

## 6.2 Timer and interrupt integration

Verify the complete path:

Hardware timer → interrupt entry → trap handling → preemption decision → scheduler → context switch → interrupt return.

Ensure the interrupt frame and stack are correct.

## 6.3 CR3 and TLB handling

Verify:

- CR3 switching.
- Page-table ownership.
- TLB invalidation.
- Address-space lifetime.
- Correct handling of kernel mappings.
- Safe process termination.

## 6.4 Ring 3 and syscall assembly

Verify:

- User-mode entry.
- System-call entry.
- System-call return.
- Register preservation.
- Stack transitions.
- Fault handling.
- Correct privilege levels.

## 6.5 Process and thread teardown

Audit concurrent termination.

A process must not free:

- An address space still in use.
- A kernel stack still executing.
- TLS state still referenced by a CPU.
- Synchronization objects with active waiters.
- Page tables still active on another CPU.

If SMP is not fully supported, explicitly document the supported CPU model and enforce safe restrictions rather than pretending SMP teardown is complete.
